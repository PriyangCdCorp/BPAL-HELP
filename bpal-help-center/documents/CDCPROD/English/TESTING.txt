CHAPTER 1 – INTRODUCTION  

1.1 Overview 

The Event Tracking System (Phase 1) is a comprehensive database-driven solution designed to capture and store system events across the entire BPAL application and services. Built with scalability and flexibility in mind, this system provides a centralized repository for all application events, establishing the foundation for future notification capabilities. 

 

“Note: This document covers Phase 1 (Data Storage). Phase 2 (Real-Time Notification System) will be planned separately once the data layer is stable.” 

1.2 Purpose 

In modern distributed systems, tracking events across multiple applications, services, and platforms presents significant challenges. Phase 1 addresses these challenges by providing: 

 

Capability 

Description 

Centralized Event Logging 

A single source of truth for all system events across BPAL 

Comprehensive Audit Trail 

Complete history of all events with timestamps and context 

Flexible Event Data Storage 

Support for structured and unstructured event data 

Event Classification 

Categorization framework for different event types and priorities 

Multi-Language Support 

Bilingual descriptions (English/French) 

User Event Subscription 

Users can subscribe to specific event configurations with per-user notification preferences and data filters 

Notification Signaling 

Lightweight kick records enable immediate notification service activation when events are logged, without impacting event insertion performance 

 

Out of Scope for Phase 1:  

Real-time notification delivery 

Email/SMS integration 

Notification queue processing 

 

1.3 Key Features 

1.3.1 Event Classification 

The system categorizes events into multiple classifications: 

 

REALTIME: Events requiring immediate notification 

NON_REALTIME: Events stored for historical reference without notifications 

CRITICAL/ERROR: High-priority events with immediate alerting 

INFO/WARNING: Informational events for monitoring 

STARTUP_EVENT/SHUTDOWN_EVENT: System lifecycle events 

1.3.2 Flexible Event Data Storage 

Events utilize a hybrid storage approach: 

Structured fields for common attributes (date, time, user, program, etc.) 

JSON-based DBEVT_DATA field for event-specific information 

Supports unlimited custom fields without schema changes 

 

1.3.3 Multi-Language Support 

The system supports bilingual descriptions and messages: 

English (_E suffix) and French (_F suffix) variants for all descriptive fields 

Configurable message templates for different locales 

 

1.3.4 User Event Subscription 

Users can subscribe to specific event types and choose to be notified when those events occur 

Each subscription supports notification preferences including preferred delivery method 

Optional filter criteria allow users to narrow notifications to only events matching specific conditions in the event data 

Subscriptions can be enabled or disabled independently without removing the configuration 

 

1.3.5 Notification Signaling 

When an event is logged, a lightweight kick record is created to signal the background Notification Service 

The kick mechanism uses Inter-Process Communication (IPC) to wake the service immediately without polling 

Kick records track processing status (Pending, Complete, Failed) for reliability 

Event classification is stored in the kick record to enable priority-based processing by the Notification Service (REALTIME/CRITICAL/ERROR processed first) 

 

 

CHAPTER 2 – SYSTEM DESIGN AND ARCHITECTURE EVOLUTION 

 

2.1 Design Philosophy 

The Event Tracking System was designed with a simple principle: Start simple, scale smartly. Rather than building a complex system upfront, we began with basic event logging and gradually added sophistication based on real-world needs. 

2.2 The Core Design – Understanding the Foundation 

Before diving into how we got here, let's look at the current core design that evolved from our iterations: 

2.2.1 The Six-Table Architecture 

EVENT_TRACKING (Main Event Storage) 

  v [Links via DBEVT_CONFIG_ID] 

EVENT_TRACKING_CONFIG_DETAIL (Program Configuration) 

  v [Links via category_id and type_id] 

EVENT_LOG_CATEGORY & EVENT_LOG_TYPE (Reference Data) 

  v [All joined in] 

USER_EVENT_TRACKING (User Subscriptions) 

  v [Filtered by user subscriptions] 

EVENT_TRACKING_KICK (Notification Signal) 

  v [Links via event_id to EVENT_TRACKING] 

USER_EVENTS_VIEW (Unified View)   

Note: Our system is built on six interconnected tables that work together.  

 

 

 

 

 

2.3 Evolution Stage 1: The Beginning 

2.3.1 Initial Challenge 

We need to track what's happening in our systems. 

2.3.2 First Design – Single Table Approach 

We started with everything in one table 

EVENT_TRACKING { 

    DBEVT_UNIQUE_ID 

    DBEVT_DATE 

    DBEVT_TIME 

    DBEVT_PROGRAM         -- Hard-coded program name 

    DBEVT_CATEGORY        -- Hard-coded like 'REPORT', 'SAMPLE', 'SCALE' 

    DBEVT_TYPE            -- Hard-coded like 'AUDITRP', 'SAMPLE', 'TSGUI-Truck Scale GUI' 

    DBEVT_DATA            -- JSON for flexibility 

} 

 

Problems emerged quickly: 

Same category spelled differently: 'Report', 'REPORT', 'report' 

No standard types across programs 

No way to know which programs were configured 

2.4 Evolution Stage 2: Introducing Reference Tables 

2.4.1 The Standardization 

We needed standardization. This led to our first major refactoring: 

EVENT_TRACKING_CATEGORY { 

    DBEVT_CATEGORY_ID       -- Now using IDs! 

    DBEVT_CATEGORY_NAME     -- 'REPORT', 'SAMPLE', 'SCALE' 

    DBEVT_CATEGORY_DESC_F/E -- Bilingual support added 

} 

EVENT_TRACKING_TYPE { 

    DBEVT_TYPE_ID 

    DBEVT_TYPE_NAME         -- 'AUDITRP', 'SAMPLE', 'TSGUI' 

    DBEVT_TYPE_DESC_F/E 

} 

But we still had a problem: How do we link events to these references without changing existing applications? 

2.5 Evolution Stage 3: The Configuration Layer 

2.5.1 The Breakthrough – Configuration Table 

This is when we introduced EVENT_TRACKING_CONFIG_DETAIL: 

EVENT_TRACKING_CONFIG_DETAIL { 

    dbevt_config_id            -- Unique config identifier 

    dbevt_program              -- Which program? 

    dbevt_category_id          -- Links to EVENT_LOG_CATEGORY 

    dbevt_type_id              -- Links to EVENT_LOG_TYPE 

    dbevt_event_classification -- REALTIME, NON_REALTIME, etc. 

} 

2.5.2 The Clever Connection 

Instead of changing EVENT_TRACKING structure dramatically, we: 

Added just one field: DBEVT_CONFIG_ID 

Applications pass config_id instead of category/type 

The config table handles all the mappings 

EVENT_TRACKING { 

    ... 

    DBEVT_CONFIG_ID     -- This one field links to everything! 

    ... 

} 

2.6 Evolution Stage 4: The Unified View 

We need to join 5 tables just to see event details! So, we created a view that does all the joining: 

USER_EVENTS_VIEW 

  - All EVENT_TRACKING fields (date, time, user, data, etc.) 

  - Program details from CONFIG_DETAIL (program, computer, classification) 

  - Category name and descriptions (English/French) 

  - Type name and descriptions (English/French) 

  - Filtered by USER_EVENT_TRACKING subscriptions 

“Note: The final fields in the tables are shown in the class diagram below in 2.8” 

2.7 Design Patterns in Our Architecture 

2.7.1 Reference Data Pattern 

EVENT_LOG_CATEGORY and EVENT_LOG_TYPE are classic reference tables 

Provide controlled vocabulary 

Support multiple languages 

 

2.7.2 Configuration Pattern 

EVENT_TRACKING_CONFIG_DETAIL centralizes program behavior 

One place to control how events are classified 

Determines real-time vs. non-real-time handling 

 

2.7.3 Facade Pattern 

USER_EVENTS_VIEW acts as a facade 

Hides complexity of joins between event, configuration, reference, and subscription tables 

Provides simple interface for user-specific event queries 

 

2.7.4 Signal Pattern 

EVENT_TRACKING_KICK acts as a lightweight notification trigger 

Decouples event storage from notification processing 

DLL inserts a kick record and signals the service via IPC, keeping event insertion fast 

Notification Service processes kick records asynchronously

2.8.7. EVENT_TRACKING_KICK (Notification Signal Table) 

Purpose: Stores lightweight signal records that notify the background Notification Service when new events require notification processing. Each record links to a specific event in EVENT_TRACKING and tracks whether the service has processed it. 

Design Philosophy: Keep event insertion fast by separating the notification signal from notification processing. The DLL inserts a minimal kick record immediately after logging an event, then signals the service via IPC. The service processes kick records asynchronously, avoiding any performance impact on the calling application.

Data Type 

Constraint

PRIMARY KEY 

Unique identifier for each kick record. Auto-incremented. 

DBETK_EVENT_ID 

INT 

FOREIGN KEY 

Reference to EVENT_TRACKING (DBEVT_UNIQUE_ID). Links this kick record to the specific event that needs notification processing. 

DBETK_STATUS 

CHAR(1) 

DEFAULT 'P' 

Processing status. 'P' = Pending (awaiting service), 'C' = Complete (processed), 'F' = Failed (error occurred). 

DBETK_CREATED_DT 

DATETIME 

DEFAULT GETDATE() 

Timestamp when the kick record was created. Set automatically at insert time. 

DBETK_PROCESSED_DT 

DATETIME 

NULL 

Timestamp when the Notification Service finished processing this record. NULL until processed. 

DBETK_PRIORITY 

INT 

DEFAULT 5 

Processing priority set by the DLL based on event classification from EVENT_TRACKING_CONFIG_DETAIL at insert time. Lower values are processed first by the Notification Service. Values: 1=REALTIME, 2=CRITICAL, 3=ERROR, 4=WARNING, 5=INFO, 6=NON_REALTIME, 7=STARTUP_EVENT, 8=SHUTDOWN_EVENT. New priority levels can be added without changes to the Notification Service. 

Business Rules: 

One kick record is created per event insert when logging is enabled, regardless of classification. The Notification Service uses the DBETK_PRIORITY to prioritize processing order. 

The DLL inserts the kick record immediately after the EVENT_TRACKING insert succeeds 

The Notification Service updates status from 'P' to 'C' or 'F' after processing 

Completed kick records can be periodically purged for housekeeping 

If the service is down, kick records accumulate with status 'P' and are processed when the service restarts 


CHAPTER 3 – HOW WE STORE THE DATA 

Our event tracking system uses a normalized database design with a configuration-based reference system. The key innovation is separating static program configuration from dynamic event data, combined with centralized logging control through a DLL interface. User subscriptions allow individual users to define which events they want to see and be notified about. 

The Core Concept: 

Three reference tables are pre-populated with master data: 

EVENT_TRACKING_CATEGORY: Defines event categories (e.g., "REPORT", "SCALE") 

EVENT_TRACKING_TYPE: Defines event types (e.g., "ADUITRP") 

EVENT_TRACKING_CONFIG_DETAIL: Contains unique program configurations 

Each program configuration is identified by a unique combination of program name and parameters, which maps to a single config_id. This config_id also stores a critical dbevt_logging_enabled flag ('Y' or 'N'). 

A fourth table, USER_EVENT_TRACKING, stores per-user subscriptions linking users to specific event configurations with notification preferences and optional filter criteria. 

A fifth table, EVENT_TRACKING_KICK, stores lightweight signal records that link to EVENT_TRACKING and notify the background Notification Service when new events need notification processing. 

How It Works: 

Step 1: Program Initialization 

When a program starts, it calls a DLL function which: 

Automatically identifies the computer and calling program name 

Captures the command-line parameters 

Looks up the matching record in EVENT_TRACKING_CONFIG_DETAIL 

Returns:  

config_id (unique identifier for this program configuration) 

logging_enabled flag ('Y' or 'N') 

Step 2: Event Logging Decision 

Throughout program execution, when events occur: 

The program checks the logging_enabled flag 

If 'Y': Proceed to log the event 

If 'N': Skip logging entirely (no database operation) 

 

Step 3: Event Recording 

When logging is enabled, the program:  

Collects event-specific details (date, time, user, sequence, data) 

Calls another DLL function to insert the event record 

Stores only:  

Runtime event data 

The config_id reference (not the full program details) 

After a successful insert, the DLL:  

Inserts a kick record into EVENT_TRACKING_KICK with the event_id, priority (mapped from event classification), and status 'P' 

Signals the Notification Service via IPC (Named Event) to process the new kick record 

The calling application returns immediately — notification processing happens asynchronously in the background service 

Every event gets a kick record. The DLL maps the event classification to a priority value in the kick record. The Notification Service processes kick records in priority order (lower values first), ensuring REALTIME and CRITICAL events are handled before INFO or NON_REALTIME events. 

Step 4: Data Retrieval 

To view complete event information: 

Query the USER_EVENTS_VIEW 

The view automatically joins EVENT_TRACKING with all reference tables and USER_EVENT_TRACKING using config_id 

Returns complete event details filtered by the user's subscriptions, including program information, categories, types, and descriptions 

Users only see events for configurations they have subscribed to
